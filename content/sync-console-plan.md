# Sync console — plan

Two lists, on this site, with links you can send: **what went into the store** and **what is
still waiting** (drafts, and priced rows with no photo). Both are generated by the daily
Gerber sync and published here automatically.

Status: **plan only — nothing built yet.** Route names and the data contract below are the
proposal; the open questions are at the bottom.

---

## 1. Why this site and not the store

The store already has `gerbersfurniture.com/product-review/` (password-protected, client-facing).
That page is good for one thing: asking the buyer to approve a batch. It is the wrong place for
our own working record:

| | Store review page | This console |
|---|---|---|
| Audience | the client | us, and any link we hand out |
| Content | drafts only | uploaded + published + drafts + blocked |
| Blocked rows (no photo) | shown as drafts | shown with the reason, filterable |
| History | last publish only | per run, with dates and totals |
| Risk | editing a live site page | none — separate deploy, separate URL |
| Data | read from WooCommerce at publish time | snapshot committed by the sync |

Keeping both is fine: the client page stays "please approve these"; the console is the ledger.

## 2. Routes

```
/sync                     overview: counts, last run, both lists summarised
/sync/uploaded            everything that went into the store, newest batch first
/sync/queue               drafts + blocked rows, with a reason on each
/api/sync                 the same data as JSON (for reuse / CSV export)
/api/sync/export          CSV of whatever the current filter selects
```

Deep links matter: `/sync/uploaded?batch=2026-11-12` and `/sync/queue?reason=no-photo` should be
shareable as-is, so filters live in the query string (`brand`, `reason`, `batch`, `q`, `page`).

If you would rather have a **separate Vercel project** with its own domain, the same code moves
unchanged — see §7.

## 3. What each page shows

**`/sync/uploaded`** — one row per product we pushed: thumbnail, name, SKU, brand, category,
price, the WooCommerce product link, and the action (`created` / `published` / `updated`).
Grouped by batch date, with per-batch totals and a copy-the-SKU-list block.

**`/sync/queue`** — one row per product NOT live, with a reason chip:

| Reason | Meaning | What clears it |
|---|---|---|
| `no photo` | priced, in the store as a draft, no image | a photo appearing (sheet or dealer harvest) — the cycle attaches it and publishes automatically |
| `no price` | in the sheet but `Display Price` is 0/blank | a price in the sheet (outside the upload set by design) |
| `held` | on `hold_skus.txt` | removing the SKU from the hold list |
| `duplicate` | SKU collides with a live product or a normalised twin | manual review only |

Totals header: uploaded today / live total / drafts / blocked-by-reason, plus "last run" timestamp.

## 4. Data contract

The sync writes **one JSON file** into this repo; the pages read only that file. No database,
no credentials, nothing to trace into the function bundle beyond a small file.

`data/gerber-sync.json`:

```jsonc
{
  "generated_at": "2026-11-12T10:38:00Z",   // when the snapshot was taken
  "sheet": { "sha256": "5f98f98…", "changed_at": "2026-11-01T12:01:48Z", "rows": 128313 },
  "run": { "uploaded": 239, "published": 145, "failed": 0 },
  "uploaded": [
    { "sku": "W1047-860", "name": "Plymouth Gray Dresser", "brand": "Flexsteel",
      "category": "Bedroom Furniture", "price": "620.99", "image": "https://…",
      "store_url": "https://gerbersfurniture.com/product/plymouth-gray-dresser/",
      "batch": "2026-11-12", "action": "published", "woo_id": 18617 }
  ],
  "queue": [
    { "sku": "1100GAC", "name": "…", "brand": "Tempur-Pedic", "category": "Bedding",
      "price": "129.00", "reason": "no photo", "batch": "2026-11-12", "woo_id": 18700 }
  ],
  "totals": { "live": 6998, "drafts": 239, "by_reason": { "no photo": 239 } }
}
```

Producer: a new `export_sync_snapshot.py` in `/opt/data/gerber_import/`, called at the end of
`sync_cycle.sh` (after publish, before the review-page rebuild). It reads the ledger, the
`reports/published_all.csv` and the store API — all things the box already has — and writes the
file. Runs whether or not the sheet changed, so the console is current every day.

## 5. How it gets to Vercel

Vercel has no access to this box and must never hold the WooCommerce keys, so the deploy carries
the data:

```
sync_cycle.sh
  └─ export_sync_snapshot.py   →  data/gerber-sync.json   (in the mriley-nextjs repo)
       └─ git add data/gerber-sync.json && git commit && git push origin main
            └─ Vercel detects the push → build (~90 s) → /sync is live
```

Guardrails:

- only `data/gerber-sync.json` is staged — never `.env`, never the SQLite DB
- the commit message is fixed (`Sync snapshot: 12 Nov — 145 published, 239 queued`) so the history stays readable
- if the push fails (network, rejected), the cycle logs it and the next run retries; the last good
  snapshot simply stays up. The page shows `generated_at`, so staleness is visible rather than hidden
- no secrets in the repo: the console needs none

**Trade-off, stated plainly:** the console is as fresh as the last cycle (≤ 24 h), not live-live.
That is the price of keeping the store keys on this box. A live version would need the WC keys in
Vercel env vars plus a server route — more moving parts, and a leak would mean a read/write key to
the store sitting in a third-party dashboard.

## 6. Phases

| # | Phase | Deliverable | Gate |
|---|---|---|---|
| P1 | Snapshot exporter | `data/gerber-sync.json` produced by the cycle, schema above | file reviewed |
| P2 | `/sync` + `/sync/uploaded` + `/sync/queue` | server-rendered pages, filters in the query string, matches the existing site styling | link live on Vercel |
| P3 | Cron wiring | snapshot committed and pushed at the end of each cycle, one commit per run | 2 clean runs |
| P4 | Polish | CSV export, per-batch deep links, `noindex`, "copy SKU list" | — |

Effort: P2 is the bulk (a few hours); P1 is small; P3 is wiring plus a failure path.

## 7. Decisions for you

| # | Question | Recommended |
|---|---|---|
| D1 | Separate Vercel project, or routes on this site? | **routes here** (`mriley-nextjs.vercel.app/sync`) — one deploy, one place to look; a domain can be pointed at it later without a code change |
| D2 | Public, `noindex`, or password-protected? | **noindex + unguessable path prefix** if you'll send it outside; add HTTP auth only if the vendor list itself is sensitive |
| D3 | Keep the store review page too? | **yes** — different audience; this one supersedes it only for our own record |
| D4 | Does the console include every blocked row, or only the priced set? | **priced set + `no price` summary count** — 121k unpriced rows would drown the page |
| D5 | Per-batch history depth | keep the **last 30 days** in the snapshot; older batches stay in `reports/published_all.csv` on this box |

## 8. What this does not change

- the sync itself, the publish rule (photo + price), the photo backfill, the store review page
- the store's own data: the console is read-only and never writes to WooCommerce
- nothing is committed to the repo except the snapshot JSON
